# Test design principles

1. **Design from the story.** Tests come from the supplied story text and any rule or decision the user confirmed during this run. The story is the source of truth.
2. **Never invent.** Do not add requirements, limits, messages, field names or expected results the story does not state. If a missing detail stops you writing an assertable expected result, ask one focused question; if it only limits depth, say so in the run summary.
3. **No repeat of BA work.** Do not run gap analysis, rewrite stories, or produce a story-analysis report. Ambiguity is raised only when it blocks meaningful test design.
4. **Technique follows the story's content, depth follows risk.** Apply every technique the story gives a basis for (positive/negative, boundary value analysis, equivalence partitioning, decision tables, state transitions, roles, lists/filters, data effects, end-to-end/integration, applicable non-functional). Do not force a technique the story has no basis for; a read-only label needs fewer cases than a payment rule, but a rule with input, role or state is explored fully.
5. **Every criterion is covered, and covered in depth.** Each acceptance criterion, business rule and testable NFR is verified by at least one case (normally two or more for an AC or BR: success, each stated failure, each partition and boundary of its data), or is explicitly listed as not testable with the reason.
6. **Complete, not minimal; distinct, not repeated.** The goal is the fullest coverage the story supports, so little is left for manual QA. Keep one case per distinct scenario: a different precondition, data partition, boundary side, role, state or outcome is a different scenario. Merge only cases with the same preconditions, partition and outcome, or that differ in wording alone. Cases are labelled by basis: `stated` (the story says it), `derived` (a variation deduced from a stated rule, tag `derived`) and `robustness` (a universal-invariant check around a stated feature, tag `robustness`). See `skills/test-coverage-design/SKILL.md`.
7. **Concise but complete.** No hard length limit: completeness, clarity and testability come before brevity. Do not repeat the story text in a case.
8. **What, not how.** Describe user or system actions and observable outcomes. Playwright code, selectors, locators and waits belong to the downstream Builder.
9. **Intermediate reasoning stays out.** Coverage notes are transient. Only the canonical test cases, the traceability metadata and the compact structured story-analysis result (an internal checkpoint under `state/analysis/`, never a report and never written into a source story) are saved. Worker transcripts are not stored.
